# UE Sim Area — design notes (2026-10-05)

Summary of the discussion that shaped this plugin, the assumptions made, and
what is still open. Written while integrating the sim developer's
`coverage_fns.py` (angular area partitioning — kept outside this repo).

## Goal

Single-robot test of **mission abstraction**: Henosync only *sets up* the
mission; all mission computation (partitioning) happens in the sim. The only
algorithm function needed right now is `Agents.BilateralInteraction`.

## What the algorithm expects

`Agents(ag_id, envi_type, nag, ang_bounds, R, ...)` — all *received* by the
algorithm, never generated by it:

| Arg          | Type                                          | Henosync field            |
| ------------ | --------------------------------------------- | ------------------------- |
| `ag_id`      | int, 1..nag                                   | Agent ID                  |
| `nag`        | int, total agents                             | Number of Agents          |
| `envi_type`  | str — only `"Circular"` usable (see below)    | Environment Type          |
| `ang_bounds` | `[start, end]` radians in [0, 2π), CCW; end < start = wraps through 0 | Angle 1 / Angle 2 (degrees, converted) |
| `R`          | number; scale only, unused by partitioning maths | Radius                 |

`BilateralInteraction(nbr_id, nbr_AoR)` merges this agent's slice with a
neighbour's slice and keeps half (which half depends on ring order).

Packet sent over TCP (ue-sim `area_port`, default 7000), one JSON line:

```json
{"angle_1": 0.0, "angle_2": 6.2814, "radius": 50.0, "ag_id": 1, "nag": 1, "envi_type": "Circular"}
```

## Decisions

- **No changes to `coverage_fns.py`** — everything accommodated on the Henosync side.
- **Per-robot packet** (not per-team). Goes through the device plugin, so it
  respects the device abstraction. Multi-robot is out of scope.
- **Angles** converted to radians and normalised to [0, 2π).
- **Whole circle = 0° → 359.9°** (360° wraps to 0 → zero-width sector).
- **ag_id / nag / envi_type** are operator inputs (defaults 1 / 1 / Circular).
  Operation fails if not 1 ≤ ag_id ≤ nag.
- **RegularPolygons removed** from the dropdown (crashes the algorithm).
- **Radius** default 50, must be > 0.

## Assumptions (unverified)

- 0 rad = sim +X axis, angles counter-clockwise.
- Circle centre is chosen by the sim (no centre is sent).
- Radius is in sim units, assumed **metres** (AirSim/ROS convention). Henosync
  only guarantees a positive value is sent.

## Test results (real `coverage_fns.py`, throwaway venv)

| Case                                              | Result |
| ------------------------------------------------- | ------ |
| 1 robot, nag=1, + neighbour id 2 at 60–180°, robot 0–60° | ✅ robot → 0–90° |
| 1 robot, 0–359.9°, + neighbour 90–180°            | ✅ robot → 0–179.9° |
| Slices that don't touch                           | ✅ unchanged |
| 3 agents, Circular                                | ✅ converges to 120° each |
| Wrap-around (-90..90°)                            | ✅ sent as [4.712, 1.571] rad |
| nag = 2                                           | ❌ both slices collapse to [0, 0] (algorithm ring logic) |
| RegularPolygons > 10 interactions                 | ❌ `UnboundLocalError: A_self` in `NbrAgents.update_info` |
| End-to-end: plugin → ue-sim `set_area` → local TCP server | ✅ packet received as above |

## Questions asked during the discussion (answered)

1. Who runs the algorithm? → The sim (mission abstraction).
2. Per-robot or per-team packet? → Per-robot; single robot only.
3. Where is the circle / 0 rad / units? → 0 rad = +X; units assumed metres; centre is the sim's choice.
4. Where do starting slices come from? → Operator enters them.
5. Should ag_id / nag / envi_type be operator inputs? → Yes.

## Open questions (for the sim developer)

1. **Neighbour inputs** — `BilateralInteraction` needs `nbr_id` and `nbr_AoR`.
   Henosync does not send them. Does the sim generate the neighbour itself, or
   should Henosync add "Neighbour ID" and "Neighbour Angle 1/2" fields to the
   packet?
2. Does the sim's TCP receiver read the new keys `ag_id`, `nag`, `envi_type`
   (Will's original packet only had `angle_1`, `angle_2`, `radius`)?
3. Confirm: 0 rad direction, circle centre, radius units.
4. Preferred way to express a whole circle (currently 0 → 359.9°).
